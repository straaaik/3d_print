# Миграции модернизации

## Этап 1 — фундамент

В Supabase Dashboard → SQL Editor выполнить целиком файл:

`supabase_migration_20260929_business_foundation.sql`

Он рассчитан на существующую схему 3D Labs. Создание новых таблиц и перенос безопасных исторических позиций выполняются одной транзакцией. Повторное применение не дублирует позиции. Миграция не пересчитывает старые цены, не списывает склад и не изменяет статусы заказов. Строки с некорректной исторической суммой/количеством пропускаются вместо выдумывания значений.

Обновлённый `supabase_schema.sql` уже содержит тот же блок. Для существующего проекта достаточно отдельной миграции; повторять весь базовый schema-файл не требуется.

Миграция проверена на отдельной локальной PostgreSQL 18. SQL на сервере Supabase агентом не выполнялся. До её применения текущие экраны продолжают использовать прежние таблицы и localStorage fallback. Следующие этапы добавят операции и дальнейшие миграции; этот файл не означает завершение всего складского функционала.

## Воспроизводимая SQL-проверка

Только в пустой одноразовой локальной PostgreSQL, не в рабочем Supabase:

1. `tests/sql/foundation-fixture.sql` создаёт минимальные legacy таблицы и двух тестовых владельцев.
2. Выполнить `supabase_migration_20260929_business_foundation.sql` дважды.
3. Выполнить `tests/sql/foundation-checks.sql` с `psql -v ON_ERROR_STOP=1`.

Успех — строка `Foundation checks passed` и код завершения 0. Fixture/checks намеренно создают и удаляют тестовые записи; на пользовательской БД их выполнять нельзя.

## Этап 2 — атомарные складские операции

После миграции этапа 1 подготовлен файл `supabase_migration_20260929_inventory_transactions.sql`. Он добавляет revision владельца, квитанции операций и RPC `business_inventory_snapshot` / `commit_business_inventory`. Обновлённый `supabase_schema.sql` содержит тот же блок. Выполнять на сервере будет пользователь.

Сохранение всех связанных таблиц — одна транзакция с блокировкой владельца, проверкой revision и idempotency key. Ошибка любого ограничения откатывает всё изменение. Существующие движения запрещено переписывать или удалять через RPC. При повторе успешно выполненной команды возвращается актуальное состояние без повторного списания.

В одноразовой локальной БД после fixture и обеих миграций выполнить `tests/sql/inventory-transactions-checks.sql`. Проверены повтор команды, конфликт revision, полный rollback, запрет смены владельца и изменения аудита, изоляция snapshot и запрет anonymous RPC. Применение миграции дважды также проверено.

## Совместимость старых заказов со складом

После двух файлов выше выполнить целиком `supabase_migration_20260930_legacy_inventory_bridge.sql`. Тот же блок включён в `supabase_schema.sql`. SQL на сервере агентом не применялся.

Миграция объединяет блокировки старых order RPC со складом, сохраняет движения и себестоимость резерва при его возврате, добавляет `business_apply_legacy_order` с квитанциями операций и расширяет snapshot исходными заказами/товарами. Финансовое редактирование заказа не меняет оценку его складского резерва. Для исторических резервов без движения фактическая себестоимость неизвестна; при возврате используется текущая средняя оценка, история заказа не переписывается.

Старые восстановление базы и восстановление каталога временно отклоняются при наличии новой истории: старый формат не содержит складской журнал. Полный backup/restore новых данных должен заменить это ограничение на этапе 6.

Локальная проверка: `tests/sql/legacy-inventory-bridge-fixture.sql`, две предыдущие миграции, bridge дважды, затем `tests/sql/legacy-inventory-bridge-checks.sql` и `tests/sql/legacy-inventory-bridge-cost-basis-checks.sql`. Проверены 72 SQL assertions, включая возврат трёх единиц по исходной себестоимости после более дорогого производства, batch delete, Undo, повтор команды, rollback и изоляцию владельца. Fixture выполнять только в пустой одноразовой PostgreSQL.

## Этап 3 — проекты и отдельные позиции заказа

После трёх файлов выше выполнить последовательно:

1. `supabase_migration_20260930_calculation_projects.sql` — признак архивной позиции и атомарный RPC сохранения проекта с проверкой его revision. При конфликте локальная версия не перезаписывает серверную; исходный черновик/очередь остаются на устройстве.
2. `supabase_migration_20260930_project_orders.sql` — nullable `orders.agreed_price` и RPC создания head + всех order_items одной транзакцией. Нулевая согласованная цена сохраняется. Новое создание из проекта не списывает материалы: резерв и производственный процесс подключаются на этапе 5.

Оба блока включены в `supabase_schema.sql`. Выполнять только эти миграции целиком в Supabase Dashboard → SQL Editor; тестовые fixture/checks на сервере не запускать. До применения приложение сохраняет проект/позиции/заказ вместе с очередью в localStorage.

Обе миграции применены дважды на одноразовой PostgreSQL 18; `tests/sql/project-orders-checks.sql` подтвердил 17 assertions: общий rollback, snapshot позиций, owner isolation, квитанции повторов, конфликт проекта и сохранение agreed_price=0. Облачная БД агентом не изменялась.

## Этап 4 — шаблоны каталога

После файлов этапов 1–3 выполнить `supabase_migration_20260930_catalog_templates.sql` целиком в Supabase Dashboard → SQL Editor. Добавлены revision, мягкое архивирование, calculation snapshot и nullable agreed_price товара; RPC объединяет metadata и opening balance одной транзакцией. Изменение шаблона и Undo сохраняют физический остаток, себестоимость склада и исторический журнал; расход материала не производится. Тот же блок включён в schema. Облачный SQL агентом не применяется; localStorage fallback сохранён.

## Этап 5 — lifecycle заказа

После миграций этапов 1–4 подготовлен supabase_migration_20261001_order_lifecycle.sql. Добавляются order revision/archive и reserved/returned quantities позиций, RPC business_apply_order с общей транзакцией head+items+stock+ledger+receipt. Миграция не печатает исторические заказы и не меняет старые snapshots. До применения очередь и цельный localStorage fallback сохраняются. SQL на сервере агентом не выполняется.

Файл прошёл gate этапа5: 85 локальных SQL assertions, два применения. Ограничены прямые записи authenticated в snapshots/ledger/heads/catalog; изменения идут через проверенные RPC. Итоговую последовательность выполнения подтвердит завершение всей задачи. Тестовые fixture/scenario файлы предназначены только для одноразовой локальной PostgreSQL, на Supabase их не запускать.

## Этап 6 — резервная копия и восстановление

После этапа 5 выполнить `supabase_migration_20261001_business_maintenance.sql` целиком. Добавляется поколение состояния (`generation`), расширенные снимки `business_inventory_snapshot` / `business_database_snapshot` и RPC `business_restore_snapshot`: одна транзакция заменяет данные только текущего владельца, сначала проверяя квитанцию и revision. До применения экспорт, сброс и восстановление работают через локальный журнал и сохранённое намерение; приложение повторит его после миграции.

Файл проверен на одноразовой локальной PostgreSQL 18 (повторное применение, 38 assertions). Точный блок включён в `supabase_schema.sql`. SQL на сервере Supabase агентом не выполнялся.
