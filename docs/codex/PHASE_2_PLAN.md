# Этап 2 — план реализации

Основа: завершённый этап 1 и неизменяемые бизнес-правила из пакета задания.

1. Чистое ядро команд склада: справочники, закупка, производство, ручная корректировка, выдача готового остатка. Оно получает полное состояние и возвращает новое, не изменяя входные данные и retail price товара.
2. Закупка обновляет остаток и средневзвешенную стоимость. Производство считает текущую себестоимость по recipe, списывает доступные граммы, фиксирует дефицит, добавляет готовые единицы с отдельной средней себестоимостью. Ручная корректировка не расходует материал.
3. Для Supabase — RPC сохранения целого изменения с блокировкой владельца, optimistic revision и квитанцией idempotency key. Реляционные таблицы, RLS и ограничения остаются основным хранилищем; изменения всех таблиц фиксируются одной транзакцией. При конфликте клиент повторяет команду на свежем состоянии. История движений не переписывается и не удаляется.
4. Local fallback — одна запись состояния вместе с очередью команд под Web Lock. При отсутствии миграции работает локально. После появления RPC очередь отправляется по порядку; при сетевой неопределённости повторяется тот же ключ. Облачный snapshot не должен затереть незавершённые локальные команды.
5. UI материала использует существующие контролы, новые NumberInput и элементы дизайн-системы. Справочники → линия → цвет, закупка и история/дефицит. В товарах отдельно «Произвести +1» и ручной остаток; в текущий каталог не вносится автоматический пересчёт retail.
6. Проверки: unit для стоимости/идемпотентности/дефицита и fallback, SQL для транзакций/CAS/изоляции/неизменности аудита, lint/typecheck/build. E2E остаются на финальный push всей работы.

Глубокий multi-item UI калькулятора и заказов вводится на последующих этапах. Выпуск ветки целиком — после этапа 6, не после промежуточного складского изменения.
