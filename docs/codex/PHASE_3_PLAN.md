# Этап 3 — многопозиционный калькулятор

Фундамент и склад завершены; бизнес-правила остаются из DECISIONS_AND_CONSTRAINTS.

1. Добавить чистую команду сохранения CalculationProject и его CalculationItem snapshot-ов в существующее цельное состояние/очередь. Сохранение заменяет позиции только этого проекта, проверяет owner/ID/quantity/recipe и сохраняет их независимые параметры. Supabase использует тот же транзакционный RPC с revision и квитанцией.
2. Вынести draft нескольких расчётов в один версионированный user-scoped кэш. Активная карточка использует существующий редактор Calculator; переключение карточок меняет только её параметры. Сохранённый проект загружается явно, без автоматического перезаписывания текущего draft облачным snapshot.
3. Добавить навигацию по карточкам, название проекта/позиции, добавление/дублирование/удаление и сравнение максимум двух позиций. Все результаты live из единого calculatePrintCost; итог проекта — calculateProjectTotals и CalculationReceipt. Никакого общего «лучше» в сравнении.
4. Разделить скидку позиции и скидку проекта; согласованная цена проекта — последний override, включая0, с отдельной корректировкой и предупреждением ниже себестоимости. В редакторе дополнительные расходы получают3 явных режима.
5. Подготовить передачу проекта в форму заказа как отдельных immutable item snapshots. Сохранение такого заказа должно атомарно создать head и order_items; параметры производства/резерва внедряются в заказный процесс этапа5.
6. Проверки: reload/10 независимых позиций/compare live, скидки/override/custom costs, сохранение/загрузка и user isolation, атомарная очередь и snapshots. Затем unit/lint/typecheck/build; E2E только перед финальным push всей ветки.

Техническое решение: расширять существующий repository командами проекта, сохраняя одну очередь и owner lock. Не создавать второй набор финансовых формул или отдельную очередь upsert для проектов. Исторические заказы не пересчитываются из изменённого проекта.
