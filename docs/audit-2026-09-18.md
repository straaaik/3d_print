### A01. Установлен Next.js с критическими бюллетенями безопасности

**Место:** [package.json:25](</G:/3d/3D Labs/package.json:25>), [package-lock.json:6296](</G:/3d/3D Labs/package-lock.json:6296>), [package-lock.json:4921](</G:/3d/3D Labs/package-lock.json:4921>).

- Next.js: [бюллетень производителя о Windows RCE](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36) затрагивает версии 16.x до 16.3.3 при размещении на Windows и использовании App/Pages Router без Cache Components. Локальная среда — Windows, Cache Components в конфигурации не включены. ОС production-хоста и его внешняя доступность не установлены; эксплуатация не проверялась.
- Next.js/sharp: [бюллетень производителя об обработке AVIF](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4) и [бюллетень sharp](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c). Риск зависит от обработки недоверенных изображений уязвимым оптимизатором; такой путь загрузки в production не подтверждён. Порог исправления, указанный бюллетенями: Next.js 16.3.3 и sharp 0.35.4 соответственно.
- js-yaml: [бюллетень о чрезмерном расходе CPU](https://github.com/advisories/GHSA-2883-xcg3-v3hh). В этом проекте пакет приходит через ESLint, то есть обнаружен в инструментах разработки, а не как подтверждённая серверная точка обработки пользовательского YAML.

**Рекомендация:** согласованно обновить Next.js/его ESLint-конфигурацию и lockfile до исправленных совместимых версий; проверить фактическую версию sharp и js-yaml после обновления, повторить audit/build/тесты. Пакеты не обновлялись: по правилам проекта для установки нужно отдельное явное разрешение.

### A02. Блокировка пользователя ограничивает интерфейс, но не прямой API

**Место:** [supabase_schema.sql:319](</G:/3d/3D Labs/supabase_schema.sql:319>), [supabase_schema.sql:384](</G:/3d/3D Labs/supabase_schema.sql:384>), [supabase_schema.sql:698](</G:/3d/3D Labs/supabase_schema.sql:698>).

Блокировка меняет `profiles.is_active`. Пользовательские политики проверяют только `auth.uid() = user_id`, а привилегированные RPC требуют непустой UID без проверки активного профиля. Владелец действующего токена после блокировки по предоставленной схеме сохраняет возможность читать и менять **свои** данные напрямую через Supabase REST/RPC, включая восстановление снимка. Auth-аккаунт также не блокируется. Это не обнаруженный доступ к чужим строкам.

**Рекомендация:** включить проверку активного существующего профиля в RLS и каждый `SECURITY DEFINER` RPC; добавить серверную блокировку Auth/отзыв сессий. Проверка только в Next.js не защищает прямой Data API — см. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

**Подтверждение:** анализ SQL и цепочки вызовов; фактические политики облачной БД не проверялись.

### A03. Поздний ответ старой сессии загрязняет кэш нового пользователя

### A04. Автономное восстановление очищает очередь, не ставя импорт на синхронизацию

**Место:** [db.ts:1512](</G:/3d/3D Labs/src/shared/api/db.ts:1512>), [db.ts:1516](</G:/3d/3D Labs/src/shared/api/db.ts:1516>), [db.ts:1555](</G:/3d/3D Labs/src/shared/api/db.ts:1555>).

При отсутствии клиента импорт пишет данные только локально и безусловно очищает всю sync queue. Импорт не создаёт новую операцию восстановления. При последующем чтении облака импортированные данные заменяются старым серверным снимком. Частичный V1-импорт ещё опаснее: импорт филаментов удаляет ожидающие операции заказов, хотя этот раздел отсутствует в копии. Подобное обнуление есть в автономных очистке/seed.

**Подтверждение:** изолированный импорт V1 с одними филаментами превратил очередь с несинхронизированным заказом в `[]`.

**Рекомендация:** сохранять атомарную операцию восстановления для будущей синхронизации; при частичном импорте не удалять очередь незатронутых разделов. Определить согласованную семантику автономных clear/seed.

### A07. Очередь не отправляется при открытии приложения уже с восстановленной сетью

**Место:** [DataProvider.tsx:215](</G:/3d/3D Labs/src/entities/model/DataProvider.tsx:215>), [DataProvider.tsx:314](</G:/3d/3D Labs/src/entities/model/DataProvider.tsx:314>).

Сценарий: изменить данные автономно → закрыть вкладку → открыть после восстановления сети. Начальная загрузка читает облако и заменяет локальный снимок. Автосинхронизация ориентирована на переход offline→online; при уже установленном `isOnline=true` сохранённая очередь может оставаться неотправленной. Операции ещё находятся в очереди, поэтому окончательная потеря всех изменений здесь не заявляется. Но пользователь видит старые данные, а новое изменение той же записи может вытеснить ожидающую операцию.

**Рекомендация:** обрабатывать очередь на старте/входе перед заменой снимка либо накладывать ожидающие операции на загруженные данные. Подтверждение — трассировка lifecycle; полный сценарий с настоящей сетью не выполнялся.

## Что работает и что осталось вне проверки

В предоставленной схеме включён RLS, есть ограничения владельца и `WITH CHECK`; изменение роли защищено серверной проверкой администратора, регистрация использует атомарное погашение ключа. Dev-вход отключён в production. Безопасные redirects и nonce-CSP покрыты unit-проверками; локальная production-проверка подтвердила основные границы. Новые шрифты локальные, renderer экспорта чека загружается по необходимости, Motion учитывает `reducedMotion`. При доступном клиенте БД восстановление направляется в атомарный RPC; отрицательные сценарии этого пути покрыты unit-тестами с mock-клиентом.

Проверка секретов ограничивалась текущими исходниками и отслеживаемыми файлами; найденных приватных ключей не было, значения `.env` не выводились. Это не проверка всей истории Git или настроек облака.

**Не проверены:** фактически применённая схема и миграции Supabase, реальные RLS-запросы нескольких аккаунтов, production-хост, его ОС и внешняя поверхность, журналы/резервные копии облака, нагрузка и большие наборы данных, FPS/Core Web Vitals, реальное восстановление после аварии, отправка писем и регистрация. Наличие локального SQL не доказывает, что он применён на сервере. В предыдущем отчёте оставалась необходимость применить атомарную миграцию 8 сентября; её текущий облачный статус неизвестен.
