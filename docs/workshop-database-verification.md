# Проверка БД мастерской

Миграция: `supabase_migration_20260923_workshop.sql`. Готова для Supabase Dashboard → SQL Editor. Тот же блок включён в `supabase_schema.sql`. Удалённая БД не изменялась.

`scripts/verify-workshop.sql` запускается после миграции на staging с двумя существующими тестовыми пользователями. Скрипт проверяет первый save, точный JSON round-trip, конфликт initial create, ограничения размеров, атомарный rollback неудачного save, пустую планировку, каскадное удаление слотов без удаления inventory, изоляцию SELECT/INSERT/UPDATE/DELETE и отсутствие доступа anon к RPC. Всё завершает ROLLBACK.

Дополнительная интеграционная проверка: создать принтер и филамент для каждого из двух пользователей; попытаться сохранить размещение чужого inventory, размещение printer в filament slot, два размещения в одном slot и два размещения одного inventory. Каждая попытка должна отклоняться внешним ключом/UNIQUE, а предыдущий snapshot и revision должны сохраняться. Удаление inventory должно удалить только соответствующее размещение.

Проверка гонки в двух SQL Editor/psql сессиях: установить одинаковый `request.jwt.claim.sub`, роль `authenticated`, прочитать revision; в обеих транзакциях вызвать `save_workshop` с этой revision. Первый вызов держать в открытой транзакции до второго вызова, затем COMMIT первого. Второй должен вернуть `WORKSHOP_REVISION_CONFLICT` (SQLSTATE 40001). При первом создании повторить с NULL: только один save должен завершиться успешно.

RPC работают как SECURITY INVOKER; таблицы доступны владельцу через RLS. Клиент обязан сохранять планировку через `save_workshop`: прямой CRUD таблиц владельцем обходит протокол revision. Геометрия пересечений и границ мебели проверяется клиентом; БД проверяет типы, базовые размеры, связи, владельца, допустимые модели, уникальность inventory и совместимость вида слота. Числа геометрии ограничены конечным диапазоном. Исходный `printers` содержит физическое оборудование пользователя, отдельный каталог не создаётся.

Статус: миграция и scripts/verify-workshop.sql успешно исполнены на изолированном PostgreSQL 18 (локальные тестовые auth/inventory таблицы и роли). Проверены round-trip, ограничения и ошибочные placements, атомарный rollback, конфликты revision, межпользовательский RLS, запрет anon, каскады и сохранение placements при восстановлении inventory. Удалённая Supabase не изменялась. Интеграция с реальной Supabase Auth и гонка двух одновременных сессий ещё не проверялись.
