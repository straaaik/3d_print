# Правила для AI-агентов (AI Agent Guidelines)

## 🌿 Правила работы с Git и ветками:
В репозитории используются две ветки:
- `main` — основная рабочая ветка (Production)
- `test` — тестовая ветка (Testing / Staging)

**Строгие правила заливки изменений:**
1. **Спрашивать пользователя**, в какую ветку залить изменения (`main` или `test`), **ТОЛЬКО если пользователь явно попросил залить/запушить изменения на GitHub**, и при этом не указал целевую ветку. Во время обычной разработки без явной команды на заливку спрашивать не нужно.
2. **Если заливка в ветку `test`**:
   - Изменения применяются, коммитятся и пушатся **ТОЛЬКО** в ветку `test`.
   - Ветка `main` не затрагивается.
3. **Если заливка в ветку `main`**:
   - Изменения применяются, коммитятся и пушатся в ветку `main`.
   - Затем ветка `main` **обязательно синхронизируется/вливается в ветку `test`** (через merge или push), чтобы тестовая ветка всегда содержала все последние изменения из `main`.

## ⚠️ Обязательное уведомление об изменениях в Supabase:
Если любая задача, новая фича или доработка требует изменений в базе данных **Supabase** (создание новых таблиц, добавление/изменение колонок, индексов, триггеров или политик RLS):
1. **Всегда сразу и явно предупреждать пользователя в ответе** о том, что требуется выполнить SQL-скрипт в Supabase.
2. **Предоставлять готовый, чистый SQL-скрипт миграции** прямо в сообщении, который пользователь сможет скопировать и выполнить в **Supabase Dashboard -> SQL Editor**.
3. **Обязательно обновлять центральный файл схемы `supabase_schema.sql`** в корне репозитория, поддерживая его в актуальном состоянии.
4. **Всегда реализовывать безопасный fallback** (на `localStorage` / кэш), чтобы приложение не падало с ошибками у пользователя даже до применения миграции в Supabase.

## 📦 Обязательное согласование библиотек:
Перед установкой, удалением или обновлением **любой прямой зависимости** (`dependencies` или `devDependencies`) агент обязан:
1. **Остановиться и запросить явное разрешение пользователя** до запуска `npm install`, `npm uninstall`, `npm update` или аналогичной команды другого пакетного менеджера.
2. Назвать точный пакет или список пакетов и объяснить:
   - какую конкретную задачу каждый пакет решает;
   - почему он выбран вместо существующего кода или ближайших альтернатив;
   - как он повлияет на bundle, runtime, поддержку и риски проекта.
3. Считать разрешение действительным только для перечисленных прямых зависимостей и согласованного объёма изменений. Обычные транзитивные зависимости выбранного пакета входят в это разрешение; новые прямые пакеты требуют отдельного согласования.
4. Не устанавливать библиотеку «на будущее»: если нет конкретного места применения, оставить рекомендацию без изменения проекта.

## ♻️ Обязательное переиспользование компонентов:
1. Перед созданием нового UI-компонента сначала проверить `src/shared/ui/` и существующие компоненты страниц.
2. Если подходящий компонент или визуальный паттерн уже существует, использовать его напрямую либо вынести общую основу в переиспользуемый shared-компонент вместо копирования разметки и стилей.
3. Новые компоненты проектировать переиспользуемыми: поведение, подписи, иконки и данные передавать через типизированные props, не привязывая компонент к одной странице без необходимости.
4. Локальный одноразовый компонент допустим только когда у него нет разумного сценария повторного использования и вынос в shared API усложнит код.

## ✅ Согласование объёма работ:
1. Если пользователь явно поручил небольшое и однозначное изменение, выполнять его без повторного запроса подтверждения.
2. Отдельный план и подтверждение пользователя требуются только для существенных изменений: новой архитектуры, нескольких связанных пользовательских сценариев, изменения модели данных или широкого рефакторинга.
3. Если для уже порученной небольшой задачи обнаружен риск или неоднозначность, способные существенно изменить результат, задать только необходимый уточняющий вопрос.

## 🎨 Обязательные правила дизайна (Meridian Cockpit Console):
**Перед созданием или редактированием ЛЮБОЙ страницы или компонента** — обязательно прочитать `DESIGN_SYSTEM.md` в корне репозитория.

**Строгие правила:**
1. **ВСЕ новые страницы и компоненты** обязаны следовать единому стилю **Meridian Cockpit Console** (эталон — страницы `/calculator` и `/orders`).
2. **Запрещено** использовать альтернативный стиль с `PageHeader`, цветными неоновыми пятнами (`blur-3xl`, `bg-[#16181d]`), радужными градиентными кнопками.
3. **Обязательные элементы каждой страницы:**
   - Обёртка: `bg-dot-grid`, футер с `§ 3D LABS · [SECTION] RUNTIME`
   - Cockpit Container: `rounded-2xl border border-white/15 bg-neutral-950/90 shadow-[0_20px_80px_-15px_rgba(0,0,0,0.9)] backdrop-blur-2xl`
   - Terminal Header: три цветные точки (🔴🟡🟢) + штамп `§ 3D-LABS // НАЗВАНИЕ_РАЗДЕЛА` + бейдж Supabase Cloud / LocalStorage
   - Кнопки действий: компонент `<CockpitButton>` со скобочной нотацией `[ текст ]`
   - Карточки/плитки: `bg-white/[0.03] border border-white/10 hover:border-white/20 rounded-xl`
   - Шрифты: `font-mono` для всех меток, значений и технических данных
   - Нижняя панель телеметрии: `border-t border-white/10 bg-neutral-950 font-mono text-[11px] text-neutral-500`
4. **Заглушки для разделов «В разработке»** — оформлять в Cockpit Console стиле с бейджем `В РАЗРАБОТКЕ` (формат: `text-amber-400 bg-amber-950/60 border-amber-800/40`), плитками планируемых модулей в стиле карточек параметров калькулятора, и `CockpitButton` для навигации.
