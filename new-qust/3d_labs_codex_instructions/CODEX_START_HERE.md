## Рекомендуемый режим работы

**По умолчанию используй поэтапный режим**, потому что задачи меняют модель данных, расчётное ядро, склад и UI одновременно. Выполняй строго по порядку:

1. `docs/codex/01_PHASE_FOUNDATION.md`
2. `docs/codex/02_PHASE_INVENTORY.md`
3. `docs/codex/03_PHASE_CALCULATOR.md`
4. `docs/codex/04_PHASE_PRODUCTS.md`
5. `docs/codex/05_PHASE_ORDERS.md`
6. `docs/codex/06_PHASE_FINAL_QA.md`

Не начинай более поздний этап, оставляя фундамент предыдущего этапа временно сломанным. После каждого этапа доводи типы, миграции/fallback и доступные проверки до согласованного состояния. Не переписывай уже завершённый слой другим несовместимым способом на следующем этапе.

Если пользователь явно просит выполнить всё одним проходом, вместо этапов используй `docs/codex/00_MASTER_PROMPT.md`.

Если пользователь отдаёт только одну конкретную задачу, соответствующий автономный промпт находится в `docs/codex/TASK_01.md` ... `TASK_07.md`.

## Неизменяемые бизнес-правила

- Фактическая прибыль заказа: **полученные оплаты − фактическая себестоимость заказа**.
- Плановую прибыль можно показывать отдельно, но не подменять ею фактическую.
- Новая закупка филамента не меняет автоматически розничную цену уже существующего товара.
- Новый товар использует актуальную средневзвешенную стоимость филамента.
- Новая физически произведённая единица существующего товара получает актуальную производственную себестоимость для учёта готового склада, но retail price автоматически не меняется.
- Нехватка готового товара или филамента не блокирует создание/выполнение заказа; показывай предупреждение и фиксируй дефицит.
- Филамент расходуется только при реальном производстве; не допускай двойных списаний.
- Физически использованный филамент не возвращается автоматически при отмене заказа после печати.
- Исторические заказы — snapshot и не пересчитываются после изменения товара, принтера или цены материала.
- `Согласованная цена` — последний override итоговой цены проекта/заказа и не изменяет себестоимость.

## Supabase

Если нужны изменения схемы, обязательно:

- создай чистую SQL migration;
- обнови корневой `supabase_schema.sql`;
- настрой RLS и нужные индексы;
- сохрани безопасный localStorage fallback до применения migration;
- подготовь понятную инструкцию пользователю, какой SQL запустить в Supabase Dashboard → SQL Editor.

Критические складские операции должны быть атомарными и идемпотентными. Не допускай частично выполненного списания/заказа.
