1. Итоговые архитектурные решения

Главное: эти задачи нельзя надежно выполнить только изменением интерфейса. Потребуются новая модель позиций заказа, складские движения, snapshot расчетов и миграции Supabase.
  • Фактическая прибыль: фиксируем как получено оплат − фактическая себестоимость. Это основной показатель в заказах и статистике. Плановая прибыль = итоговая цена − себестоимость остается справочной.
  • Цена существующего товара: новая закупка филамента меняет weighted average сырья, но не переписывает существующий товар автоматически. Новый товар использует актуальную среднюю цену. Существующий — только после явного пересчета/редактирования.
  • Готовый товар и заказ: недостаток готового товара не блокирует заказ. Готовый остаток сначала используется/резервируется, оставшееся становится production need.
  • Производство +1 после создания заказа: филамент списывается при +1. Перед дальнейшим производством заказа система снова использует доступный готовый остаток, чтобы не списать пластик повторно.
  • Статусы: в текущем коде нет статуса «В работе». Фактический производственный порог — «Печать». Прямой переход на более поздний статус/«Готово» также должен инициировать недостающее производственное списание один раз.
  • После печати пластик назад не возвращается: отмена/откат статуса после фактического производства не восстанавливает катушку. Годное изделие возвращается только как готовый товар отдельным действием.
  • Дефицит филамента: недостаток не блокирует. Баланс остается 0, а непокрытые граммы фиксируются как deficit/audit record с предупреждением.
  • Цена и себестоимость готовой продукции — разные вещи: retail/final price существующего товара не меняется от новых закупок сырья, но каждая новая произведенная единица должна получить актуальную производственную себестоимость на момент производства. Для готового склада веди weighted-average unit cost (или эквивалентный cost basis через stock movements). При выдаче готовых единиц в заказ себестоимость order item snapshot берется из этого cost basis; изделия, произведенные специально под заказ, фиксируют текущую себестоимость производства. Это сохраняет корректность формулы payment − cost без автоматического изменения цены каталога.
  • Ключ к надежности: order items, inventory ledger, snapshot-ы и атомарные операции Supabase. Без этого UI-правки приведут к double-spend и изменению истории.

Что уже видно в текущем коде

  • Текущий Filament хранит только name, weight_g, price, color; цена материала рассчитывается как price / weight_g.
  • SavedCalculation уже является основой товара и содержит stock_quantity, но себестоимость/цена товара хранятся агрегировано.
  • Order сейчас имеет один product_id, поэтому multi-item заказ потребует отдельной модели позиций.
  • Статусы заказа: «Не в работе», «Моделирование», «Ждет печати», «Печать», «Ждет покраски», «Покраска», «Ждет отправки», «Отправлен», «Готово».
  • В OrderFormModal сейчас прибыль местами считается как amount - cost, а при выборе товара новый заказ может сразу получить оплату на всю сумму — это нужно изменить.
  • calculateOrdersSummaryKPI сейчас также использует amount - cost; статистика должна быть синхронизирована с новой семантикой оплаты.
  • Плюс проекта: calculatePrintCost уже делегирован в централизованный src/shared/lib/formulas.ts. Его стоит расширять, а не создавать новые формулы на каждом экране.
  • AGENTS.md требует SQL-миграцию, обновление supabase_schema.sql, безопасный fallback и соблюдение правил веток.

3. Отдельный промпт для каждой задачи

Эти промпты можно отправлять по одному. Для минимизации переделок лучше использовать поэтапную последовательность из раздела 5, если агент будет работать несколькими заходами.

Задача 1. Склад филамента: справочники, закупки, средняя цена и расход

Ты работаешь в существующем проекте 3D Labs (Next.js 16 / React 19 / TypeScript / Supabase / localStorage fallback). Сначала прочитай AGENTS.md и релевантные файлы проекта. Реализуй полноценный склад филамента, не ломая существующие данные и сохраняя fallback до применения SQL-миграции.

Цель: заменить текущую плоскую модель филамента (name/weight_g/price/color) на структурированный учет материала и его движений.

Требования:
1. Добавь справочник производителей филамента: Bambu Lab, eSUN, Polymaker и т.п. Пользователь может добавлять/редактировать свои значения.
2. Добавь отдельный справочник базовых типов материала: PLA, PETG, ABS, ASA, TPU и т.п. Пользователь может добавлять свои типы. Сложность материала должна определяться по типу, а не парсингом полного названия.
3. Модель карточки: Производитель + базовый тип + линейка/название материала (например Bambu Lab / PLA / PLA Matte). Внутри карточки — варианты по цветам. Физические катушки отдельно не учитывать.
4. Конкретный цвет/вариант хранит текущий остаток в граммах и средневзвешенную закупочную цену. Пользователь при закупке вводит вес и общую стоимость; цена за кг рассчитывается автоматически.
5. Повторная закупка того же варианта не создает дубликат, а увеличивает остаток и пересчитывает средневзвешенную цену: (старый остаток * старая цена/г + новый вес * новая цена/г) / новый общий остаток. При расходе средняя цена не меняется.
6. Храни историю закупок: дата, вес, общая цена, цена/кг, вариант филамента.
7. Введи журнал движений филамента (ledger): purchase, production_order, production_stock, manual_adjustment и при необходимости другие явные типы. Каждое движение должно иметь источник/reference ID и быть идемпотентным, чтобы один заказ/позиция не мог списать материал дважды.
8. Производственный расход списывается, когда заказ впервые достигает фактического производства: статус «Печать» или любой более поздний производственный/финальный статус, если пользователь перескочил через «Печать». Переходы назад/вперед не должны повторно списывать уже учтенное.
9. Если заказ использует готовый товар со склада, филамент списывается только за количество, которое реально необходимо изготовить, а не за готовые экземпляры.
10. Если филамента недостаточно, заказ/производство НЕ блокировать. Остаток филамента не уводить ниже 0. Создать/зафиксировать дефицит по конкретному материалу и показать предупреждение «Не хватает N г». Дефицит должен оставаться аудируемым в истории.
11. После фактической печати отмена заказа не возвращает филамент в катушку. Если изделие пригодно, его можно вернуть в готовую продукцию отдельным складским действием.
12. Критические складские операции в Supabase должны быть атомарными (предпочтительно RPC/database function/transaction pattern), чтобы заказ, движения склада и остатки не расходились при частичной ошибке.
13. Обнови типы TypeScript, API/db layer, localStorage fallback/миграцию локальных данных, RLS, индексы и supabase_schema.sql. Предоставь отдельный чистый SQL migration script согласно AGENTS.md.
14. Старые записи филамента мигрируй безопасно, без потери данных: если производитель/тип/линейка неизвестны, используй нейтральные legacy-значения и дай пользователю затем отредактировать их.

Критерии готовности: средняя цена корректна после нескольких закупок; расход не дублируется; остатки не отрицательные; дефицит виден; старые данные открываются; без Supabase-миграции приложение продолжает работать через fallback; build/lint/typecheck по доступным скриптам проходят.

Задача 2. Прибыль только по фактической оплате

В проекте 3D Labs унифицируй финансовую логику заказов. Прочитай AGENTS.md и существующий formulas.ts, Orders, Stats.

Главное правило: основная фактическая прибыль заказа = текущая сумма полученных оплат - фактическая себестоимость заказа.

Примеры:
- Цена заказа 100, себестоимость 60, оплачено 0 => прибыль -60.
- Оплачено 50 => прибыль -10.
- Оплачено 100 => прибыль 40.
- Оплачено 120 => прибыль 60.

Требования:
1. Используй одну централизованную функцию фактической прибыли во всех местах: таблица заказов, строка/карточка/Drawer, модальное окно, сортировка, сводка, статистика/KPI.
2. Статус заказа не должен сам по себе менять прибыль.
3. Новый заказ по умолчанию имеет payment=0 и payments=[]; выбор товара не должен автоматически помечать его полностью оплаченным.
4. Переплата разрешена и увеличивает фактическую прибыль.
5. Основной показатель «Прибыль» в заказах — именно payment - cost.
6. В подробном чеке дополнительно можно показывать справочный показатель «Плановая прибыль» = итоговая цена заказа - себестоимость, но не подменять им фактическую прибыль.
7. Для общей статистики раздели, где это полезно, «объем заказов/начислено» и «получено оплат». Фактическую чистую прибыль считай на основе полученных оплат и себестоимости; существующие отдельные expense-заказы учитывай как расходы согласно текущей модели.
8. Не меняй историческую себестоимость старых заказов при изменении товаров/филамента.
9. Добавь тестовые сценарии для частичной оплаты, нулевой оплаты, полной оплаты и переплаты.

Проверь calculateOrdersSummaryKPI и все места, где сейчас используется amount - cost: они должны быть приведены к новой единой семантике для фактической прибыли.

Задача 3. Несколько расчётов в калькуляторе, общий итог и сравнение

Расширь калькулятор 3D Labs с одной детали до проекта из нескольких независимых расчетных позиций. Не создавай набор разрозненных calcWeight1/calcWeight2 state-полей: введи нормальную модель CalculationProject -> CalculationItem[].

Требования:
1. В одном проекте может быть несколько деталей/вариантов. У каждого CalculationItem собственный стабильный ID, название, количество и полный набор параметров существующего калькулятора: филамент, принтер, вес, время, труд, брак, наценка, дополнительные расходы, срочность, скидка и т.д.
2. Добавь кнопку «Добавить расчёт». Новый чек появляется впереди, предыдущий визуально уходит назад красивой анимацией, но не исчезает. Добавь компактную навигацию/список или tabs/chips, чтобы удобно переключаться даже при 8-10 позициях.
3. Поле «Количество» умножает материальные/временные/ценовые показатели корректно согласно существующим правилам per-unit/fixed.
4. На уровне детали поддерживай индивидуальную скидку. На уровне всего проекта — отдельную общую скидку. Не применять одну скидку дважды.
5. Отдельный блок общего итога в реальном времени: количество позиций, общее число изделий, расход материала (с разбивкой по филаментам при необходимости), время, себестоимость, сумма до общей скидки, скидки, итоговая цена, плановая прибыль, маржа.
6. Режим «Сравнить»: пользователь выбирает максимум 2 расчёта. Показать материал, вес, количество, время, себестоимость материала, полную себестоимость, цену, прибыль, маржу, электричество, амортизацию, труд, дополнительные расходы, скидки. Обновление live.
7. Система не пишет «лучше» и не выбирает победителя. Разрешена только смысловая подсветка отдельных метрик: ниже лучше для себестоимости/времени/расхода; выше лучше для прибыли/маржи; цену клиенту не объявлять победителем, можно показать разницу нейтрально.
8. Проект должен сохраняться и открываться позже (Supabase + local fallback). Название проекта редактируется.
9. Из проекта можно создать один заказ. Каждая CalculationItem становится отдельной order item со snapshot всех параметров и расчетов на момент создания. Старые order items не должны меняться при будущих изменениях товара/филамента.
10. Не дублируй формулы: используй единый calculation engine. UI чека вынеси в переиспользуемый CalculationReceipt, но формы редактирования могут быть разными.
11. Обнови типы, API, schema/migration при необходимости и local fallback.

Критерии: переключение не теряет state; проект восстанавливается после перезагрузки; сравнение live; общий итог корректен; создание заказа сохраняет несколько позиций без потери расчетных деталей.

Задача 4. Модальное окно заказа: полноценные чеки по каждой детали и NumberInput

Переработай второй блок «Финансы и оплаты» в модальном окне создания/редактирования заказа 3D Labs.

Требования по чекам:
1. Если в заказе несколько деталей/order items, показывай отдельный полноценный чек для каждой детали, а не один общий упрощенный чек.
2. Каждый чек должен отражать ту же детализацию, что расчет в калькуляторе: название, количество, выбранный филамент, расход/стоимость материала, электричество, амортизация, технологический брак, труд, дополнительные расходы, наценка, срочность, скидка детали, себестоимость единицы/тиража, цена клиенту, плановая прибыль, маржа и другие реальные составляющие calculation engine.
3. Используй общий CalculationReceipt/единые форматтеры и расчетное ядро, чтобы калькулятор, товары и заказы не расходились по формулам/дизайну.
4. Если заказ создается вручную, пользователь может добавлять детали и редактировать все параметры расчета прямо в модальном окне, с live-пересчетом.
5. Помимо чеков деталей оставь общий финансовый блок заказа: суммарная себестоимость, сумма деталей, скидка всего заказа, согласованная/итоговая цена (если применяется), оплачено, осталось оплатить, фактическая прибыль = payment - cost. Плановую прибыль можно показывать отдельно.

Требования по числовым полям:
6. Исправь UX, когда начальный 0 мешает вводу. Создай/улучши общий NumberInput: если текущее значение 0, пользователь при фокусе/начале ввода сразу может набрать 120 без получения 0120 и без ручного удаления нуля.
7. Ненулевое существующее значение не стирай просто от фокуса.
8. Разреши временно пустую строку и корректный ввод десятичных значений; нормализуй обязательное пустое значение в 0 по blur/commit. Учти русскую запятую и точку, если существующий UX это допускает.
9. Примени компонент ко всем релевантным числовым полям заказа и по возможности переиспользуй в калькуляторе/товарах, не ломая controlled state.

Не упрощай order item до ссылки на текущий товар: заказ должен хранить snapshot расчетных данных.

Задача 5. Товары: полное inline-редактирование и режим редактирования через калькулятор

Расширь раздел «Товары» 3D Labs. Существующая раскрывающаяся строка товара с анимацией должна стать полноценным редактором расчета товара.

Требования:
1. В раскрытом блоке разреши менять название, принтер, конкретный вариант филамента/цвет, вес, время печати, количество/базовые параметры, ручной труд, технологический брак, дополнительные расходы, наценку, скидку, срочность и остальные параметры calculation engine.
2. Все изменения пересчитывают preview/чек в реальном времени, но в базу пишутся только после «Сохранить изменения». Добавь «Отменить изменения» и индикатор несохраненных изменений.
3. Показывай полный CalculationReceipt с той же структурой, что в калькуляторе. Формулы и отображение должны использовать общие модули, а не копии.
4. Редактирование товара НЕ списывает филамент: товар — шаблон/расчет, не факт производства.
5. Кнопка «Открыть в калькуляторе» переносит все параметры конкретного товара и его ID в калькулятор. Вверху явно покажи «Редактирование товара: <название>».

Задача 6. Заказы при нулевом складе: не блокировать, корректно использовать готовый товар и филамент

Исправь складскую логику создания и выполнения заказов в 3D Labs. Недостаток готового товара или филамента не должен блокировать создание заказа.

Готовый товар:
1. Если stock_quantity=0, заказ все равно сохраняется. Покажи неблокирующее уведомление «Товара нет в наличии на складе». Остаток не становится отрицательным.
2. Если на складе 2, а заказали 5: заказ сохраняется; 2 готовых экземпляра резервируются/используются со склада, остаток становится 0, а 3 фиксируются как количество, которое требуется изготовить. Покажи «Недостаточно товара на складе».
3. Храни snapshot по каждой order item: ordered_quantity, quantity_from_stock/reserved, quantity_to_produce/remaining_to_produce и фактически произведенное/учтенное количество. Не пересчитывай прошлое по текущему складу без явной операции.
4. Если после создания заказа пользователь производит +1 товар в каталоге, это отдельная операция «Произвести на склад»: готовый stock +1 и филамент списывается сразу по сохраненному рецепту товара.
5. Перед производственным списанием по заказу система должна снова использовать доступный незарезервированный готовый stock для покрытия оставшейся потребности. Это предотвращает двойной расход, если товар был произведен на склад после создания заказа. После этого филамент списывается только за реально остающееся quantity_to_produce.
6. «+ / Произвести» и «Ручная корректировка склада» должны быть разными операциями. Производство +1 списывает филамент и фиксирует фактическую unit cost новой готовой единицы по текущему расчету; обновляй weighted-average cost basis готового stock без изменения retail/final price товара. Корректировка исправляет учетное количество без производственного расхода и требует/позволяет указать причину. Уменьшение stock не возвращает филамент.
7. Когда заказ забирает готовые единицы со склада, фиксируй их себестоимость в OrderItem из текущего finished-stock cost basis. Единицы, произведенные непосредственно под заказ, фиксируют фактическую производственную себестоимость на момент производства. Общая order cost складывается из этих snapshot-стоимостей и других расходов.
8. Производственный расход заказа срабатывает один раз при первом достижении статуса «Печать» или любого более позднего статуса при перескоке. Если уже списано/произведено — повторные переходы не списывают снова.
9. Если филамента недостаточно для требуемого производства, заказ не блокировать, баланс филамента не делать отрицательным: списать доступное до 0 и зафиксировать дефицит N г с material ID и source/order item. Показать предупреждение.
10. После реальной печати отмена/откат статуса не возвращает использованный пластик автоматически.
11. Сделай ledger готовых товаров и/или минимум аудируемые движения stock: reservation/order fulfillment, production_stock, manual_adjustment, return_to_stock и т.п. Критические Supabase-изменения атомарны и идемпотентны.
12. Удали существующее блокирующее условие не только из UI, но и из save/API/database logic.

МИГРАЦИЯ/ОБРАТНАЯ СОВМЕСТИМОСТЬ:
- Старые filaments сохранить; legacy manufacturer/type/line назначить безопасно и позволить редактировать позже.
- Старые SavedCalculation/Order открыть без падений.
- Старый orders.product_id можно временно сохранить для backward compatibility, но новая логика должна опираться на order_items.
- Старые single orders при миграции можно представить как один order item snapshot, где это возможно.
- localStorage данные версионировать/мигрировать, не просто очищать.

ТЕСТЫ/ACCEPTANCE SCENARIOS:
1. Закупки 500г по 20/кг + 1000г по 24/кг => средняя 22.67/кг; расход не меняет average.
2. Заказ 5, готово 2 => stock 0, need produce 3; material только на произведенные 3.
3. После создания такого заказа production_stock +1 списывает material один раз; перед запуском заказа эта 1 единица может покрыть часть remaining, после чего material заказа списывается только на оставшиеся 2.
4. Direct status «Не в работе» -> «Готово» списывает нужный material один раз; «Печать» -> «Готово» второй раз не списывает.
5. Filament stock 120г, need 300г => заказ идет дальше, stock 0, deficit 180г и warning.
6. Новая закупка материала меняет average, но существующий Product retail price не меняется автоматически; новый Product использует новый average; явный recalc существующего — меняет после подтвержденного действия. Новая произведенная единица существующего Product получает актуальную production cost в finished-stock cost basis без изменения retail price.
7. Новый Order из Product: payment 0, actual profit = -cost. Частичная/полная/переплата дают ожидаемые значения.
8. Multi-item calculator сохраняет/восстанавливает проект, live aggregate и compare работают; order создается со всеми item snapshots.
9. Order modal показывает отдельный receipt каждой детали; manual order items считаются тем же engine.
10. Product inline edit: live preview, Cancel откатывает, Save сохраняет; edit-in-calculator update vs save-as-new работают по ID.
11. Agreed price выше/ниже расчетной и ниже cost работает с корректировкой/warning.
12. Все 3 custom cost modes дают математически ожидаемый результат.
13. Никаких отрицательных stock balances для готовых товаров/филамента; движения и deficits аудируемы.

5. Если не отдавать один большой промпт: правильная последовательность

Ниже задачи разбиты не по пользовательским номерам, а по техническим зависимостям. Это уменьшает вероятность, что агент сначала построит UI на старой модели, а потом будет переписывать его заново.

  1. Фундамент: schema/types/migrations, order items, projects, calculation engine, NumberInput.
  2. Склад: филамент, закупки, weighted average, ledgers, finished stock.
  3. Калькулятор: multi-item project, compare, aggregate, agreed price/custom costs.
  4. Товары: inline editor и связь с calculator.
  5. Заказы: receipts, actual profit, production fulfillment, stock/filament расход.
  6. Интеграция: stats, migrations/fallback, tests, build и ревизия на double-spend.

Этап 1 — фундамент: модель данных, миграции и единое ядро

Работаем над проектом 3D Labs. Это первый этап большой модернизации. Сначала прочитай AGENTS.md и текущую архитектуру. На этом этапе НЕ надо доводить все UI-фичи; задача — создать фундамент без ломки существующего приложения, чтобы следующие этапы не переделывали модель.

Сделай:

3. Сохрани backward compatibility: legacy filaments, saved_calculations, orders.product_id. Продумай backfill старых single order -> one order item там, где безопасно.
4. Версионируй/мигрируй localStorage fallback вместо очистки.
5. Укрепи calculation engine: единые типы результата, planned profit, подготовка project-level totals, CustomCostItem mode enum (profit_only/cost_with_markup/cost_no_markup), agreed-price final override. Legacy custom costs не должны менять старые суммы.
6. Создай единый NumberInput и базовый CalculationReceipt (presentational), но пока не переписывай все экраны целиком.
7. Добавь/обнови unit tests расчетного ядра: три custom cost mode, agreed price, quantity, discount/urgency.
8. Существующее приложение после этапа должно по-прежнему открываться даже до применения миграции Supabase благодаря fallback/feature-safe parsing.

В конце дай SQL, список измененных файлов и результаты tests/typecheck/lint/build. Не начинай глубокую UI-переделку следующих этапов.

Этап 2 — склад филамента и готовой продукции

Это второй этап. Предполагается, что фундамент/типы/миграции этапа 1 уже внедрены. Не меняй заново базовую модель без необходимости.

Реализуй склад:
1. UI производителей, типов, линий/карточек и color variants филамента.
2. Закупки variant: вес + общая цена; weighted average; purchase history; stock grams.
3. Material difficulty теперь берется из material type.
4. Filament ledger и deficit handling. Недостаток не блокирует, stock floor 0, deficit N г + toast/warning.
5. Готовый stock: раздели «Произвести +1» (списывает material по recipe товара и фиксирует current production unit cost) и «Ручная корректировка» (не списывает material, аудируется). Поддерживай weighted-average finished-stock unit cost отдельно от retail/final price Product.
6. Finished stock movements/ledger; при выдаче готового stock в OrderItem сохраняй snapshot его cost basis. Не возвращай filament при простом уменьшении stock.
7. Критические операции сделай идемпотентными и атомарными в Supabase; local fallback обновляй цельным состоянием.
8. Изменение weighted average не должно автоматически пересчитывать существующие товары; подготовь возможность показать предложение пересчета.

Проверь закупки по разным ценам, несколько цветов одной линии, производство +1, manual adjustment, недостаток material.

Этап 3 — новый многопозиционный калькулятор

Это третий этап после фундамента и складов.

Этап 4 — товары и связь с калькулятором

Это четвертый этап. Новый calculation engine/project уже существует.

Обнови Products:
1. Существующая раскрывающаяся строка -> полноценный editor всех расчетных параметров + CalculationReceipt.
2. Live preview; Save/Cancel; dirty indicator и предупреждение ухода.
3. Редактирование не списывает material и не меняет stock_quantity.

Этап 5 — заказы, чеки, оплаты и производственное списание

Это пятый этап. Схема order_items, склад и calculator/project уже готовы.

Полностью интегрируй Orders:
1. Один Order содержит много OrderItem snapshots. Manual order может добавлять/редактировать items тем же calculation engine.
2. В блоке «Финансы и оплаты» отдельный CalculationReceipt для каждой детали + общий financial summary.
3. Actual profit везде = payment - cost; planned profit показывай только как дополнительный показатель. Новый order payment=0, payments=[]; product selection не создает auto-payment.
4. Обнови Orders row/table/drawer/modal/filter/sort/summary и Stats/KPI на единую семантику фактической прибыли. При необходимости показывай отдельно ordered revenue и received payments.
5. Finished stock shortage не блокирует: reserve/use available stock, remainder to produce. Stock не отрицательный. Себестоимость использованных готовых единиц snapshot-ится из finished-stock weighted cost basis; retail price товара от этого не меняется.
6. Перед производством заказа используй новый доступный unreserved stock для покрытия remaining; filament списывай только на остаток.
7. Производственное списание запускается один раз при первом достижении «Печать» или любого более позднего статуса при skip. Повторные status transitions идемпотентны.
8. Filament shortage не блокирует: stock 0 + deficit + warning.
9. Уменьшение stock/откат статуса не возвращает уже физически использованный filament.
10. NumberInput применить ко всем релевантным финансовым/числовым полям модалки.
11. Все multi-table Supabase changes по order production делай атомарно.

Особенно протестируй: stock2/order5; +1 production_stock после order creation; затем запуск order => material не списывается дважды; direct «Не в работе» -> «Готово»; частичная оплата/переплата.

6. Контрольный список перед тем, как считать работу законченной

Склад филамента
  • Weighted average считается правильно.
  • Расход не меняет average.
  • Нехватка не блокирует, deficit виден.
  • Одинаковое событие не списывает дважды.
Готовый склад
  • Никаких отрицательных остатков.
  • Заказ может превышать stock.
  • Production +1 ≠ manual correction.
  • Новый stock после заказа может покрыть remaining без double-spend.
Финансы
  • Actual profit = payment-cost везде.
  • Новые orders не auto-paid.
  • Planned profit отделен.
  • Переплата поддерживается.
История
  • Старые orders не меняются от Product update.
  • Existing Product не auto-reprice от purchase.
  • OrderItem — snapshot.
  • Ledger/audit сохраняет источники.
Калькулятор
  • Несколько items сохраняются/reload.
  • Aggregate/compare live.
  • Item + global discount не дублируются.
  • Agreed price — последний override.
Технически
  • SQL migration готов.
  • supabase_schema.sql обновлен.
  • RLS/индексы есть.
  • Fallback работает до миграции.
  • Lint/typecheck/tests/build проверены.

Рекомендуемые ручные сценарии smoke-test

  1. Купить 500 г по 20/кг, затем 1000 г по 24/кг → средняя 22,67/кг.
  2. Создать заказ 5 шт. при stock=2 → stock=0, remaining production=3, заказ сохранен.
  3. После этого сделать Production +1 в товарах → material списан один раз; затем запустить заказ → дополнительный material только на оставшиеся 2.
  4. Перевести заказ сразу «Не в работе» → «Готово» → материал списан один раз. Затем сменить статус туда‑сюда → второго списания нет.
  5. Нужно 300 г, доступно 120 г → stock filament=0, deficit=180 г, заказ не заблокирован.
  6. Купить тот же filament дороже → existing Product retail price прежняя; новый Product считает по новой средней; явный recalc existing меняет только после действия пользователя. Затем произвести +1 existing Product → retail price прежняя, но finished-stock unit cost учитывает текущую себестоимость.
  7. Order cost=60, payment 0/50/100/120 → profit -60/-10/40/60.
  8. Создать 3 детали в Calculator, сохранить, перезагрузить, сравнить 2, создать один Order с 3 OrderItems.
  9. Отредактировать Product inline → Cancel откатывает, Save сохраняет; открыть в Calculator → Update обновляет ID, Save as new создает новый.
  10. Расчет 3500 → agreed 5000 дает adjustment +1500; agreed ниже cost показывает warning, но сохраняется.
  11. Проверить profit_only / cost_with_markup / cost_no_markup на одной и той же сумме.

7. Что я бы не делал

  • Не хранить новые multi-item заказы только одним product_id и JSON без snapshot-семантики.
  • Не списывать филамент простым if status === ... then stock -= ... без ledger/idempotency.
  • Не менять цены всех существующих товаров автоматически после закупки сырья.
  • Не возвращать физически использованный пластик при отмене уже напечатанного заказа.
  • Не создавать три независимые формулы и три независимых чека для Calculator / Product / Order.
  • Не решать проблему нуля через стирание любого значения на focus — это испортит редактирование существующих чисел.
  • Не блокировать бизнес-процесс из-за учетного дефицита; лучше показать дефицит и сохранить аудит.
