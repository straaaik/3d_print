# Master prompt — все задачи одним проходом

Ты работаешь в существующем репозитории 3D Labs. Нужно выполнить связанный набор доработок целиком, не как разрозненные UI-патчи. Стек проекта: Next.js 16.3.1, React 19, TypeScript, Tailwind 4, Supabase + localStorage fallback. Сначала прочитай AGENTS.md, package.json, supabase_schema.sql, src/shared/types, src/shared/lib/formulas.ts, DataProvider, db.ts и релевантные Calculator / Filaments / Products / Orders / Stats компоненты. Next.js-специфичные изменения делай с учетом локальных docs, как требует AGENTS.md.

ВАЖНО ПО ПРОЦЕССУ:
- Не останавливайся после каждой мелкой подзадачи; выполни весь доступный объем последовательно и в конце дай отчет.
- Не делай commit/push без соблюдения правил AGENTS.md. Если пользователь не указал ветку и git-операция реально требуется, спроси ветку один раз перед git-операциями; кодовые изменения/анализ из-за этого не блокируй.
- Любые изменения Supabase: подготовь чистый SQL migration script, обнови supabase_schema.sql, RLS/индексы и сохрани безопасный localStorage fallback до применения миграции.
- Существующие данные и старые заказы не должны молча менять исторические значения после миграции.
- После работы выполни доступные lint/typecheck/build/tests; если что-то нельзя запустить из-за окружения, явно сообщи.

АРХИТЕКТУРНЫЕ ПРИНЦИПЫ (ОБЯЗАТЕЛЬНО):
1. Раздели сущности: Product/SavedCalculation = производственный шаблон; Finished stock = уже изготовленные экземпляры; Filament = сырье; OrderItem = immutable/snapshot расчетных параметров конкретной позиции заказа.
2. Заказ должен поддерживать несколько order items. Нельзя ограничиваться одним orders.product_id. Введи order_items (таблица или эквивалентная нормализованная модель с RLS; предпочтительно таблица) и snapshot параметров/стоимостей.
3. Введи CalculationProject -> CalculationItem[] для нескольких расчетов. Не размножай одиночные calc* state-поля по индексам.
4. Оставь/усиль единое расчетное ядро в src/shared/lib/formulas.ts или выделенном модуле. Калькулятор, товары и заказы не должны иметь разные формулы.
5. Выдели переиспользуемый CalculationReceipt для отображения чека. Формы редактирования могут отличаться; не делай один гигантский универсальный form-компонент.
6. Складские операции должны быть идемпотентны и аудируемы через ledger. Критические Supabase-операции — атомарны (RPC/database function или эквивалент), чтобы остатки, order items и движения не расходились.
7. Введи общий NumberInput, который корректно работает с 0, временно пустой строкой и decimals.

ЗАДАЧА 1 — ФИЛАМЕНТ / СЫРЬЕ:
- Добавь справочники производителей и базовых типов материала. Пользователь может добавлять свои значения.
- Структура: Manufacturer -> Material type -> Product line/name (например Bambu Lab / PLA / PLA Matte) -> color variants.
- Физические катушки отдельно не учитывать.
- Variant хранит current_stock_g и weighted_average_cost (лучше цена/г или цена/кг как derived), цвет/диаметр и ссылки на manufacturer/type/line.
- Закупка: пользователь вводит вес и общую стоимость. Сохраняй purchase history. Повторная закупка того же variant увеличивает остаток и пересчитывает средневзвешенную цену; расход среднюю цену не меняет.
- Сложность/наценку материала определяй по material type, не по парсингу display-name.
- Введи filament_movements ledger с source/reference и уникальностью/идемпотентностью.
- Нехватка филамента не блокирует заказ/производство. Остаток не уходит ниже 0; фиксируется material deficit N г с источником и предупреждением.
- После реальной печати отмена не возвращает пластик автоматически.

ЗАДАЧА 2 — ФАКТИЧЕСКАЯ ПРИБЫЛЬ:
- Главная формула: actualProfit = totalPaymentsReceived - actualOrderCost.
- 100 цена / 60 cost / 0 paid => -60; 50 paid => -10; 100 => 40; 120 => 60.
- Применить централизованно в Orders table/row/drawer/modal, сортировке, summary и Stats/KPI.
- Новый заказ по умолчанию payment=0, payments=[]; выбор товара не делает заказ полностью оплаченным.
- Дополнительно в подробностях можно показывать plannedProfit = finalOrderAmount - cost, но основной «Прибыль» — фактический.
- В статистике различай «объем заказов/начислено» и «получено оплат», если это нужно для ясности; фактическая прибыль базируется на оплатах.

ЗАДАЧА 3 — МНОГОПОЗИЦИОННЫЙ КАЛЬКУЛЯТОР:
- CalculationProject содержит несколько CalculationItem с независимыми параметрами и quantity.
- Кнопка «Добавить расчёт»: новый чек впереди, старый анимированно уходит назад, но остается доступным. Добавь удобную навигацию по позициям для больших наборов.
- Скидка каждой детали + отдельная общая скидка проекта.
- Общий live итог: позиции, изделия, материал, время, себестоимость, скидки, итог, planned profit, margin.
- Сравнение максимум двух расчетов live, без вывода «лучше». Смысловая зеленая подсветка отдельных метрик допустима; цену клиенту сравнивай нейтрально.
- Проект сохраняется в Supabase + fallback и открывается позже.
- Из проекта создается один заказ, каждая деталь -> OrderItem snapshot.

ЗАДАЧА 4 — МОДАЛЬНОЕ ОКНО ЗАКАЗА:
- Во втором блоке «Финансы и оплаты» показывай отдельный полноценный CalculationReceipt для каждой order item.
- В каждом: материал/расход/стоимость, электричество, амортизация, брак, труд, custom costs, markup, urgency, item discount, base cost, price, planned profit, margin и остальные реальные составляющие engine.
- При ручном заказе разреши создавать/редактировать позиции с теми же параметрами и live расчетом.
- Общий финансовый итог заказа: total cost, item totals, order-level discount, agreed/final price, paid, due, actual profit = paid-cost.
- Исправь ввод 0 через общий NumberInput: 0 не мешает сразу вводить 120; ненулевое не стирать от focus; пустое допустимо во время ввода; нормализация по commit/blur; decimals не ломать.

ЗАДАЧА 5 — ТОВАРЫ:
- Раскрывающаяся строка товара становится полноценным editor: name, filament variant/color, printer, weight, print time, labor, defect, custom costs, markup, urgency, discount и все расчетные параметры.
- Live preview, но запись в БД только по «Сохранить изменения»; «Отменить изменения» и dirty-state warning.
- Полный CalculationReceipt внутри раскрытия.
- Редактирование товара не списывает филамент.
- «Открыть в калькуляторе» переносит весь расчет и product ID. Покажи «Редактирование товара: <name>».
- «Обновить товар» обновляет исходный ID; «Сохранить как новый товар» создает новый ID.
- Старые заказы не меняются.
- НОВОЕ ПРАВИЛО ЦЕНЫ ФИЛАМЕНТА: изменение weighted average материала не должно автоматически переписывать retail/final price существующего товара. Новый товар рассчитывается по текущей средней стоимости. Существующий товар принимает новую расчетную retail price только после явного пересчета/редактирования. При этом фактический cost basis готового склада ведется отдельно: новые произведенные единицы получают текущую себестоимость производства, которая входит в weighted-average cost готового stock, но не меняет цену каталога.

ЗАДАЧА 6 — ГОТОВЫЙ СКЛАД И ВЫПОЛНЕНИЕ ЗАКАЗА:
- Недостаток готового товара никогда не блокирует создание заказа.
- stock=0, order=1: заказ сохранен, stock остается 0, informational warning.
- stock=2, order=5: 2 используются/резервируются, stock -> 0, remaining_to_produce=3, warning.
- Храни на order item ordered_quantity, from_stock/reserved, remaining_to_produce/produced/accounted значения, чтобы история не зависела от будущего stock.
- Если после создания заказа пользователь сделал +1 товар в каталоге, это production_stock: stock +1 и филамент списывается тогда же.
- Перед списанием по заказу используй доступный незарезервированный готовый stock для покрытия remaining_to_produce; затем филамент списывай только за реально остающиеся изделия. Это предотвращает двойное списание.
- Раздели «Произвести +1» и «Ручная корректировка stock». Production +1 списывает филамент, фиксирует текущую фактическую unit cost и обновляет weighted-average finished-stock cost basis; retail/final price товара при этом не меняется. Корректировка не списывает/не возвращает филамент автоматически и аудируется с причиной.
- При использовании готового stock в заказе snapshot себестоимости берется из finished-stock cost basis; то, что производится специально под заказ, фиксирует текущую production cost.
- Производство заказа запускает расход при первом достижении статуса «Печать» либо любого более позднего статуса при прямом перескоке («Ждет покраски», «Покраска», «Ждет отправки», «Отправлен», «Готово»). Ранние статусы «Не в работе», «Моделирование», «Ждет печати» сами по себе материал не списывают.
- Повторные переходы/сохранения не создают дубль движения.
- Недостаток филамента: не блокировать, stock floor 0, deficit record + warning.
- Уменьшение готового stock не возвращает филамент.

ЗАДАЧА 7 — СОГЛАСОВАННАЯ ЦЕНА И CUSTOM COST MODES:
- На уровне всего CalculationProject/заказа добавь «Согласованная цена» как последний override.
- Пример 3500 расчет -> agreed 5000: строка «Корректировка до согласованной цены +1500», final 5000. Можно вводить ниже расчетного; если ниже себестоимости — warning, не блокировка.
- Корректировка не меняет себестоимость, только final price/planned profit.
- Три явных режима CustomCostItem (enum, не набор двусмысленных boolean):
  1) profit_only — в цену, не в cost;
  2) cost_with_markup — в cost и на сумму применяется markup;
  3) cost_no_markup — в cost и в цену 1:1 без дополнительной прибыли.
- Сохрани isPerUnit/fixed и enabled.
- Legacy custom costs мигрируй без неожиданного изменения старых итогов; их текущее поведение в существующем engine проанализируй и выбери соответствующий default (ожидаемо cost_no_markup для большинства старых данных).
- Единый pipeline расчета должен быть явно описан и протестирован; agreed price применяется последним.

МИГРАЦИЯ/ОБРАТНАЯ СОВМЕСТИМОСТЬ:
- Старые filaments сохранить; legacy manufacturer/type/line назначить безопасно и позволить редактировать позже.
- Старые SavedCalculation/Order открыть без падений.
- Старый orders.product_id можно временно сохранить для backward compatibility, но новая логика должна опираться на order_items.
- Старые single orders при миграции можно представить как один order item snapshot, где это возможно.
- localStorage данные версионировать/мигрировать, не просто очищать.

ТЕСТЫ/ACCEPTANCE SCENARIOS:
1. Закупки 500г по 20/кг + 1000г по 24/кг => средняя 22.67/кг; расход не меняет average.
2. Заказ 5, готово 2 => stock 0, need produce 3; material только на произведенные 3.
3. После создания такого заказа production_stock +1 списывает material один раз; перед запуском заказа эта 1 единица может покрыть часть remaining, после чего material заказа списывается только на оставшиеся 2.
4. Direct status «Не в работе» -> «Готово» списывает нужный material один раз; «Печать» -> «Готово» второй раз не списывает.
5. Filament stock 120г, need 300г => заказ идет дальше, stock 0, deficit 180г и warning.
6. Новая закупка материала меняет average, но существующий Product retail price не меняется автоматически; новый Product использует новый average; явный recalc существующего — меняет после подтвержденного действия. Новая произведенная единица существующего Product получает актуальную production cost в finished-stock cost basis без изменения retail price.
7. Новый Order из Product: payment 0, actual profit = -cost. Частичная/полная/переплата дают ожидаемые значения.
8. Multi-item calculator сохраняет/восстанавливает проект, live aggregate и compare работают; order создается со всеми item snapshots.
9. Order modal показывает отдельный receipt каждой детали; manual order items считаются тем же engine.
10. Product inline edit: live preview, Cancel откатывает, Save сохраняет; edit-in-calculator update vs save-as-new работают по ID.
11. Agreed price выше/ниже расчетной и ниже cost работает с корректировкой/warning.
12. Все 3 custom cost modes дают математически ожидаемый результат.
13. Никаких отрицательных stock balances для готовых товаров/филамента; движения и deficits аудируемы.
