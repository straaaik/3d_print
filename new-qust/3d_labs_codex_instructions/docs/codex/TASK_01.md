# Задача 1 — склад филамента, справочники, закупки и расход

Ты работаешь в существующем проекте 3D Labs (Next.js 16 / React 19 / TypeScript / Supabase / localStorage fallback). Сначала прочитай AGENTS.md и релевантные файлы проекта. Реализуй полноценный склад филамента, не ломая существующие данные и сохраняя fallback до применения SQL-миграции.

Цель: заменить текущую плоскую модель филамента (name/weight_g/price/color) на структурированный учет материала и его движений.

Требования:
1. Добавь справочник производителей филамента: Bambu Lab, eSUN, Polymaker и т.п. Пользователь может добавлять/редактировать свои значения.
2. Добавь отдельный справочник базовых типов материала: PLA, PETG, ABS, ASA, TPU и т.п. Пользователь может добавлять свои типы. Сложность материала должна определяться по типу, а не парсингом полного названия.
3. Модель карточки: Производитель + базовый тип + линейка/название материала (например Bambu Lab / PLA / PLA Matte). Внутри карточки — варианты по цветам. Физические катушки отдельно не учитывать.
4. Конкретный цвет/вариант хранит текущий остаток в граммах и средневзвешенную закупочную цену. Пользователь при закупке вводит вес и общую стоимость; цена за кг рассчитывается автоматически.
5. Повторная закупка того же варианта не создает дубликат, а увеличивает остаток и пересчитывает средневзвешенную цену: (старый остаток * старая цена/г + новый вес * новая цена/г) / новый общий остаток. При расходе средняя цена не меняется.
6. Храни историю закупок: дата, вес, общая цена, цена/кг, вариант филамента.
7. Введи журнал движений филамента (ledger): purchase, production_order, production_stock, manual_adjustment и при необходимости другие явные типы. Каждое движение должно иметь источник/reference ID и быть идемпотентным, чтобы один заказ/позиция не мог списать материал дважды.
8. Производственный расход списывается, когда заказ впервые достигает фактического производства: статус «Печать» или любой более поздний производственный/финальный статус, если пользователь перескочил через «Печать». Переходы назад/вперед не должны повторно списывать уже учтенное.
9. Если заказ использует готовый товар со склада, филамент списывается только за количество, которое реально необходимо изготовить, а не за готовые экземпляры.
10. Если филамента недостаточно, заказ/производство НЕ блокировать. Остаток филамента не уводить ниже 0. Создать/зафиксировать дефицит по конкретному материалу и показать предупреждение «Не хватает N г». Дефицит должен оставаться аудируемым в истории.
11. После фактической печати отмена заказа не возвращает филамент в катушку. Если изделие пригодно, его можно вернуть в готовую продукцию отдельным складским действием.
12. Критические складские операции в Supabase должны быть атомарными (предпочтительно RPC/database function/transaction pattern), чтобы заказ, движения склада и остатки не расходились при частичной ошибке.
13. Обнови типы TypeScript, API/db layer, localStorage fallback/миграцию локальных данных, RLS, индексы и supabase_schema.sql. Предоставь отдельный чистый SQL migration script согласно AGENTS.md.
14. Старые записи филамента мигрируй безопасно, без потери данных: если производитель/тип/линейка неизвестны, используй нейтральные legacy-значения и дай пользователю затем отредактировать их.

Критерии готовности: средняя цена корректна после нескольких закупок; расход не дублируется; остатки не отрицательные; дефицит виден; старые данные открываются; без Supabase-миграции приложение продолжает работать через fallback; build/lint/typecheck по доступным скриптам проходят.
