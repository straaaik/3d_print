# Задача 3 — несколько расчётов, общий итог и сравнение

Расширь калькулятор 3D Labs с одной детали до проекта из нескольких независимых расчетных позиций. Не создавай набор разрозненных calcWeight1/calcWeight2 state-полей: введи нормальную модель CalculationProject -> CalculationItem[].

Требования:
1. В одном проекте может быть несколько деталей/вариантов. У каждого CalculationItem собственный стабильный ID, название, количество и полный набор параметров существующего калькулятора: филамент, принтер, вес, время, труд, брак, наценка, дополнительные расходы, срочность, скидка и т.д.
2. Добавь кнопку «Добавить расчёт». Новый чек появляется впереди, предыдущий визуально уходит назад красивой анимацией, но не исчезает. Добавь компактную навигацию/список или tabs/chips, чтобы удобно переключаться даже при 8-10 позициях.
3. Поле «Количество» умножает материальные/временные/ценовые показатели корректно согласно существующим правилам per-unit/fixed.
4. На уровне детали поддерживай индивидуальную скидку. На уровне всего проекта — отдельную общую скидку. Не применять одну скидку дважды.
5. Отдельный блок общего итога в реальном времени: количество позиций, общее число изделий, расход материала (с разбивкой по филаментам при необходимости), время, себестоимость, сумма до общей скидки, скидки, итоговая цена, плановая прибыль, маржа.
6. Режим «Сравнить»: пользователь выбирает максимум 2 расчёта. Показать материал, вес, количество, время, себестоимость материала, полную себестоимость, цену, прибыль, маржу, электричество, амортизацию, труд, дополнительные расходы, скидки. Обновление live.
7. Система не пишет «лучше» и не выбирает победителя. Разрешена только смысловая подсветка отдельных метрик: ниже лучше для себестоимости/времени/расхода; выше лучше для прибыли/маржи; цену клиенту не объявлять победителем, можно показать разницу нейтрально.
8. Проект должен сохраняться и открываться позже (Supabase + local fallback). Название проекта редактируется.
9. Из проекта можно создать один заказ. Каждая CalculationItem становится отдельной order item со snapshot всех параметров и расчетов на момент создания. Старые order items не должны меняться при будущих изменениях товара/филамента.
10. Не дублируй формулы: используй единый calculation engine. UI чека вынеси в переиспользуемый CalculationReceipt, но формы редактирования могут быть разными.
11. Обнови типы, API, schema/migration при необходимости и local fallback.

Критерии: переключение не теряет state; проект восстанавливается после перезагрузки; сравнение live; общий итог корректен; создание заказа сохраняет несколько позиций без потери расчетных деталей.
